# 핫딜 · 관심도 기반 추천 피드 계획

> 상태: M0~M4 구현 완료, 머지 전 — 에픽 [#271](https://github.com/whsanha55/scoophub/issues/271), PR [#273](https://github.com/whsanha55/scoophub/pull/273).
> 진행 현황은 16절.
>
> 별도 저장소 [feedforge](https://github.com/whsanha55/feedforge)(`docs/PLAN.md` v2)로 시작한 계획을
> scoophub로 합쳤다. scoophub에 이미 있는 수집·알림·LLM·인증·UI 구성은 그대로 재사용하고,
> 새로 만드는 것은 핫딜 소스와 개인화 추천 루프뿐이다.

## 1. 개요

핫딜을 주기적으로 수집하고, 개인 관심도 프로필과 대조해
관련성이 높은 항목을 웹 추천 피드로 제공한다.

사용자는 웹에서 항목을 확인하고 좋아요·싫어요 피드백을 남긴다.
피드백은 관심도 프로필에 반영되어 추천이 개인 취향에 맞게 조정된다.

Telegram은 추천 항목 전체를 전달하는 수단이 아니라,
놓치면 아쉬운 중요 항목만 알려주는 보조 알림 채널로 쓴다.

핵심 가치

- 개인화: 모든 수집 항목이 아니라 관심에 맞는 항목을 보여준다.
- 편리한 피드백: 웹에서 여러 항목을 확인하고 간편하게 평가한다.
- 학습: 명시적 피드백이 이후 추천에 반영된다.
- 선택적 알림: 웹에 방문하지 않아도 중요한 항목은 놓치지 않는다.

> 찾아보면 내 관심에 맞는 피드가 준비되어 있고,
> 놓치면 아쉬운 항목만 먼저 알려준다.

### 1.1. scoophub 기존 구성과의 관계

| 필요 기능 | 사용하는 scoophub 구성 |
|---|---|
| 수집 실행·스케줄·실행 기록 | `global/crawl`의 `Crawler`·`CrawlRunner`, `crawl_config`, `crawl_logs` |
| Telegram 알림·중복 발송 방지 | `global/notify`의 `NotifyRouter`·`TelegramNotifier`, `notify_route`, `notify_log` |
| LLM 관련성·제외 판정 | `external/llm`의 `LlmClient` |
| 인증·권한 | Google OAuth, `SUPER_EMAILS`, `@SuperOnly` |
| 웹 화면 | Next.js 프런트엔드(`app/(app)`, `domains/`) |
| GitHub·Hacker News 수집 | 이미 수집 중 → 개인화 점수 적용 대상으로 검토 (12절 M5) |

feedforge 고유 기능 중 새로 만드는 것:

1. 핫딜 소스 수집 (뽐뿌 RSS, 확장 후보 클리앙)
2. 관심도 프로필 → 스코어링 → 추천 피드 → 피드백 → 가중치 학습 → 재평가

## 2. 서비스 범위

### 2.1. v1 전제

- 추천 피드는 단일 사용자(관리자) 전용이다. 프로필·피드백·설정은 사용자 구분 없이 하나만 둔다.
- 웹 추천 피드를 주 인터페이스로 제공한다.
- 모바일 브라우저에서도 쓸 수 있는 반응형 화면을 제공한다.
- Telegram 알림을 꺼도 수집·추천·피드백은 정상 동작한다.
- 추천은 키워드·카테고리 기반으로 시작한다.
- LLM은 추천 후보의 관련성·제외 판정(8.4)에만 제한적으로 쓴다.
- 임베딩, 벡터 DB, 별도 메시지 큐는 도입하지 않는다.

### 2.2. 채널별 역할

| 기능 | 웹 | Telegram |
|---|---|---|
| 추천 확인 | 개인화 피드 | 중요 항목 알림 |
| 좋아요 / 싫어요 | 주 피드백 수단 | 후순위 선택 기능 |
| 이전 항목 탐색 | 필터·히스토리 | 웹 링크로 이동 |
| 관심도 관리 | 관심·제외 키워드 관리 | 제공하지 않음 |
| 알림 설정 | 활성화·상한·조용한 시간 | 설정에 따라 수신 |

## 3. 기술 스택

scoophub 스택을 그대로 쓴다. feedforge에서 정한 Spring Boot 3, JVM 21,
Vite SPA, 정적 Bearer 인증은 쓰지 않는다.

| 항목 | 선택 | 비고 |
|---|---|---|
| 백엔드 | Kotlin 2.4, Spring Boot 4.1, Java 25 | scoophub `backend/` |
| DB | PostgreSQL + Flyway | scoophub DB에 테이블 추가 |
| 스크래핑 | Jsoup | scoophub에 이미 있는 의존성 |
| HTTP 클라이언트 | Spring RestClient | |
| 프런트엔드 | Next.js 16, React 19, Tailwind CSS 4 | scoophub `frontend/` |
| 인증 | Google OAuth + `@SuperOnly` | 피드 조회 공개 여부는 14절 |
| LLM | `LlmClient` | 모델·호출 상한은 14절 |
| 배포 | scoophub `deploy.sh` | 별도 컨테이너 없음 |

## 4. 아키텍처

```
┌──────────────────────────────────────────────────────┐
│                scoophub backend                      │
│                                                      │
│  CrawlRunner (crawl_config 스케줄)                    │
│    └─ 핫딜 Crawler (ppomppu, zod 중지)               │
│       → hotdeal_item 저장 / 최신 메타데이터 갱신       │
│       → 추천 평가 트리거                               │
│                                                      │
│  ScoringService                                      │
│    └─ 관심도 프로필 대조                              │
│       → 추천 후보 평가 → hotdeal_feed_item 저장       │
│                                                      │
│  REST API (/api/hotdeal/* , @SuperOnly)              │
│    ├─ 추천 피드 조회                                  │
│    ├─ 좋아요 / 싫어요 / 취소                          │
│    ├─ 관심도 프로필 관리                              │
│    └─ 알림 설정                                      │
│                                                      │
│  FeedbackService                                     │
│    └─ 피드백 상태 변경 → 프로필 갱신 / 로그 저장       │
│                                                      │
│  알림                                                │
│    └─ 높은 점수의 추천만 선별 → NotifyRouter          │
└──────────────────────────────────────────────────────┘
```

### 설계 원칙

- 수집, 추천, 알림을 분리한다.
- 웹 추천 여부와 Telegram 발송 여부를 별도로 관리한다.
- 외부 HTTP 호출 중 긴 DB 트랜잭션을 유지하지 않는다.
- 수집기 하나의 실패가 다른 소스의 수집을 막지 않게 한다. (`CrawlRunner`가 소스별로 격리한다)
- 추천 후보를 모아 평가한 뒤 알림을 선정한다.
- 특정 소스의 수집 순서가 일일 알림 예산을 독점하지 않게 한다.
- scoophub 컨벤션과 `docs/convention/LOCAL.md`를 따른다.
  `ApiResponse` 래핑, `ResponseStatusException` 에러, Service 경유 데이터 접근 등이 해당한다.

## 5. 수집 소스

| 소스 | 주소 / 방식 | 주요 수집 필드 | 상태 |
|---|---|---|---|
| 뽐뿌 | 공식 RSS `rss.php?id=ppomppu` | 몰·상품명·가격·배송(제목에서 분리)·추천수·게시 시각 | M1, 15분 주기 |
| 알구더 | zod.kr/deal HTML | 제목·몰·가격·배송비·추천수 | 구현했지만 중지 (Cloudflare 403) |
| 클리앙 알뜰구매 | clien.net/service/board/jirum HTML | 미정 | 확장 후보 (robots.txt 허용) |

2026-10-14 확인 결과 (feedforge 계획의 소스 재검토):

- 알구더: Cloudflare 봇 차단으로 403. 수집기와 파서는 남겨 두고 스케줄만 껐다 (V42).
- FM코리아: HTTP 200 이지만 robots.txt 가 일반 봇에 `/hotdeal` 을 금지한다. 수집하지 않는다.
- 아카라이브·퀘이사존: 403.
- 뽐뿌: 공식 RSS 를 robots.txt 가 막지 않는다. RSS 는 최근 15건만 주므로 15분 주기로 수집한다.
  `hits` 는 `[댓글|조회|추천|비추천]` 으로 보고 세 번째 값을 추천수로 쓴다 (관찰 기반 가정).

소스는 robots.txt 와 이용 정책을 먼저 확인하고, 막혀 있으면 우회하지 않는다 (13절).
저장된 HTML·RSS fixture 로 파서 회귀 테스트를 구성한다.

GitHub trending, Hacker News, 테크 뉴스는 scoophub가 이미 수집한다.
이 데이터에 개인화 점수를 적용할지는 M5에서 검토한다. 적용하더라도 새로 수집하지 않는다.

확장 후순위: 클리앙, 쿨엔조이.

## 6. 웹 화면

scoophub 프런트엔드에 `app/(app)/hotdeal`과 `domains/hotdeal`로 추가한다.

### 6.1. 추천 피드 — 메인 화면

웹에서도 전체 수집 목록이 아니라 **개인화된 추천 목록**을 기본 제공한다.

주요 기능

- 추천순 / 최신순 정렬
- 소스 필터
- 원문 이동
- 좋아요 / 싫어요 / 피드백 취소
- 현재 피드백 상태 표시
- 추천 이유 표시
- 페이지네이션 또는 더 보기
- 모바일 반응형 레이아웃

카드 예시

```
WD SN850X 2TB — 149,000원
뽐뿌 · G마켓 · 배송 무료 · 20분 전
추천 이유: SSD, 저장장치 관심
[원문 보기] [👍 관심 있음] [👎 관심 없음]
```

동작 정책

- 피드백은 화면에 즉시 반영한다.
- 싫어요 항목은 기본 피드에서 숨긴다.
- 숨긴 항목은 별도 필터에서 확인하고 피드백을 취소할 수 있다.
- 딜 종료·품절 정보가 확인되면 카드에 표시한다.
- 내부 추천 점수는 상세 정보로 제공하고, 기본 화면에서는 추천 이유를 강조한다.

### 6.2. 좋아요 목록

- 좋아요한 항목 모아보기
- 소스 필터
- 원문 이동
- 좋아요 취소

v1에서는 별도 북마크를 만들지 않는다.
"관심 있음"과 "나중에 보기"를 구분할 필요가 생기면 그때 분리한다.

### 6.3. 관심도 및 알림 설정

- 관심 키워드 추가 / 삭제
- 제외 키워드 관리
- 카테고리 가중치 관리
- 필요 시 학습값 초기화
- Telegram 알림 활성화 / 비활성화
- 알림 임계치 / 일일 상한
- 조용한 시간 설정

## 7. 데이터 모델

`crawl_data` JSON이 아니라 전용 테이블을 쓴다.
중복 제거, 재평가, 피드백 연결에 컬럼과 제약조건이 필요하기 때문이다.

아래는 논리 모델 초안이다. 실제 타입과 인덱스는 마이그레이션 작성 시 확정한다.
테이블 이름에는 `hotdeal_` 접두어를 붙인다. scoophub의 `feed_*`(뉴스 등) 테이블과 구분하기 위해서다.

```sql
-- 수집 원본
hotdeal_item (
  id,
  source,                 -- PPOMPPU | ZOD
  provider,               -- 실제 공급자 구분 (없으면 source와 같은 값)
  source_key,
  category,
  title,
  url,
  canonical_url,
  extra JSONB,
  item_at,                -- 확인 가능한 원본 게시 시각
  first_seen_at,
  last_seen_at,
  updated_at,
  availability,           -- UNKNOWN | AVAILABLE | ENDED
  UNIQUE(source, provider, source_key)
)

-- 관심도 프로필
hotdeal_interest_profile (
  id,
  kind,                   -- KEYWORD | CATEGORY | SOURCE
  value,
  seed_weight,            -- 수동 설정 기준값
  learned_weight,         -- 피드백에 의한 변화량
  updated_at,
  UNIQUE(kind, value)
)

-- 웹 추천 결과
hotdeal_feed_item (
  id,
  raw_item_id,
  score,
  matched_terms JSONB,    -- 매칭 항목·당시 가중치·점수 기여도
  judgment JSONB,         -- LLM 관련성·제외 판정 결과·사유·모델·판정 입력 해시
  scoring_version,
  recommended_at,
  evaluated_at,
  expires_at,
  UNIQUE(raw_item_id)
)

-- 현재 피드백 상태
hotdeal_feedback (
  id,
  feed_item_id,
  kind,                   -- LIKE | DISLIKE
  channel,                -- WEB | TELEGRAM
  created_at,
  updated_at,
  UNIQUE(feed_item_id)
)

-- 피드백 변경 및 학습 이력
hotdeal_feedback_log (
  id,
  feedback_event_id,
  feed_item_id,
  profile_id,
  previous_kind,
  new_kind,
  delta,
  previous_weight,
  new_weight,
  reason,
  created_at,
  UNIQUE(feedback_event_id, profile_id)
)

-- 알림 설정은 테이블 대신 crawl_config('hotdeal_notify').params 로 둔다 (9.1)
```

feedforge 계획의 `notification_delivery`는 만들지 않는다.
발송 채널·대상은 `notify_route`, 발송 결과와 중복 방지는 `notify_log`(route + payload key)를 쓴다.
`notify_log`로 9.3절 정책을 지키지 못하는 부분이 있으면 M4에서 보완한다.

### 모델 정책

- `provider`는 필수값으로 정규화해 고유 제약에 NULL이 들어가지 않게 한다.
- 같은 원본을 다시 수집하면 추천수·가격·상태 등 변경 가능한 필드를 갱신한다.
- 추천 항목의 점수는 갱신할 수 있지만, 이미 발송한 항목은 다시 발송하지 않는다.
- 피드백 취소 시 현재 상태를 제거하고 변경 이력을 남긴다.
- 매칭된 프로필 항목이 없는 피드백도 `profile_id` NULL·`delta` 0으로 이력 1건을 남긴다.
- 현재 모델은 단일 사용자 전제다.
  다중 사용자로 확장하면 프로필·추천·피드백·알림 설정에 사용자 식별자를 추가한다.
- 감사 필드(`created_at`/`updated_at`)는 DB 기본값, 비즈니스 시각은 `Clock`으로 채운다 (LOCAL.md).

## 8. 스코어링 규칙

### 8.1. 기본 방식

```
score(item)
  = 매칭된 키워드 가중치 합
  + 매칭된 카테고리 가중치
  + 소스 가중치
  + 소스별 인기 보너스
```

추천 조건

- 관심 키워드 또는 관심 카테고리가 하나 이상 매칭되어야 한다.
  단, 콜드스타트 온보딩(8.3) 동안에는 인기 기반 노출로 대체한다.
- 총점이 웹 추천 임계치 이상이어야 한다.
- 관련성·제외 판정(8.4)과 신선도 조건을 통과해야 한다.

초기 정책

- 종자 프로필 없이 시작한다 (콜드스타트, 8.3)
- 웹 추천 임계치: 3.0을 임시 시작값으로 쓴다
- 웹에서 추가한 키워드의 기본 seed_weight는 임계치와 함께 확정한다 (14절)
- 인기 보너스: 소스별 계수와 상한 적용
- 같은 관심 항목은 한 게시물에서 한 번만 가산
- 영문 짧은 키워드는 단순 부분 문자열 대신 토큰 경계 매칭
- 한국어 부분 문자열 오탐(예: "램" → "램프")은 관련성 판정(8.4)으로 거른다
- 동의어는 소규모 사전으로 시작
- 소스 가중치는 v1에서 수동 관리

임계치는 관찰 모드 결과와 실제 피드백 패턴을 보고 조정한다.

### 8.2. 피드백 학습

| 입력 | 처리 |
|---|---|
| 좋아요 | 매칭된 관심 항목 강화 |
| 싫어요 | 매칭된 관심 항목 약화 |
| 취소 | 기존 피드백의 학습 효과 되돌리기 |
| 무반응 | 변화 없음 |
| 조회 / 원문 클릭 | v1에서는 학습에 사용하지 않음 |

- 좋아요·싫어요의 초기 총 변화량은 각각 +0.5, -0.5를 검토한다.
- 여러 프로필 항목이 매칭되면 총 변화량을 나누어 적용한다.
- 유효 가중치에는 상한과 하한을 둔다.
- 학습 대상은 키워드·카테고리이며, 소스 가중치는 자동 변경하지 않는다.
- 피드백 변경 시 이전 효과를 되돌린 후 새 효과를 적용한다.
- 학습 이력에는 실제 적용된 변화량을 기록한다.
- 같은 피드백을 반복 제출해도 추가 학습하지 않는다.
- 피드백 상태 변경과 프로필 갱신은 같은 트랜잭션에서 처리한다.

무반응을 싫어요로 간주하지 않는다.

장기 시간 감쇠가 필요해지면 게시물별 무반응 패널티 대신
학습값이 종자값으로 천천히 복귀하는 방식을 별도 검토한다.

### 8.3. 콜드스타트 (종자 프로필 없이 시작)

초기 키워드 없이 시작하므로 프로필이 형성될 때까지 별도 동작이 필요하다.

- 온보딩 단계: 관심 키워드·카테고리를 웹 설정 화면에서 직접 추가한다.
  추가된 키워드는 seed_weight로 등록되고 즉시 스코어링에 반영된다.
- 프로필 항목이 부족한 동안(예: 관심 항목 5개 미만)은
  인기 보너스(추천수) 기준 피드를 함께 노출해 피드백을 남길 소재를 제공한다.
  이 항목은 웹 추천 임계치 대신 소스별 인기 상위 기준으로 선정하고,
  추천 이유를 "인기 항목"으로 표시한다.
- 노출된 항목에 좋아요·싫어요를 남기면 매칭된 키워드·카테고리 후보가
  자동으로 프로필에 추가되는 방식을 검토한다 (명시적 확인 절차 포함).
- 온보딩 단계의 인기 기반 노출은 프로필 형성 후 자동으로 줄인다.
- 가중치는 웹 설정 화면에서 수동으로도 조정할 수 있다 (6.3절).

### 8.4. 관련성·제외 판정 (LLM)

키워드 단순 매칭은 오탐(특히 한국어 부분 문자열)과 제외 누락이 많으므로,
점수 조건을 통과한 후보를 LLM으로 한 번 더 판정한다. 호출은 `LlmClient`를 쓴다.

- 점수 조건을 통과한 추천 후보에만 적용해 호출량을 제한한다.
- 입력: 제목·카테고리·소스, 매칭된 관심 키워드, 등록된 제외 키워드·설명.
- 출력: 관련 여부·제외 여부와 짧은 사유. 결과는 `hotdeal_feed_item.judgment`에 저장한다.
- 관련 없음 또는 제외로 판정된 항목은 기본 피드에서 숨기고,
  숨긴 항목 필터에서 사유와 함께 확인한다.
- 콜드스타트 인기 노출 항목(매칭 키워드 없음)은 제외 여부만 판정한다.
- 판정 입력(매칭 키워드·제외 조건)이 같으면 기존 결과를 재사용한다.
- LLM 호출이 실패하면 관련성 판정은 통과로 두고, 제외는 제외 키워드 단순 매칭으로 대체한다.
  실패 항목은 다음 수집 주기에 재판정한다.

### 8.5. 재평가

프로필이 바뀌어도 과거 항목이 반영되도록 신선도 기간 내 항목을 다시 평가한다.

- 대상: 신선도 기간(10절) 안의 `hotdeal_item` 전체.
  임계치 미달로 `hotdeal_feed_item`이 없던 항목도 포함한다.
- 키워드 추가·삭제, 가중치 수동 변경 시: 즉시 재평가한다.
- 피드백 학습에 의한 가중치 변화: 다음 수집 주기에 몰아서 재평가한다.
- 새로 임계치를 넘은 항목은 `hotdeal_feed_item`을 생성한다.
- 임계치 아래로 내려간 항목은 삭제하지 않고 기본 피드에서만 숨긴다.
  이미 피드백한 항목은 점수와 관계없이 유지한다.
- 재평가로 LLM 판정 입력이 바뀐 항목만 재판정한다 (8.4).
- 이미 발송한 항목은 재평가 결과와 관계없이 다시 발송하지 않는다.

## 9. Telegram 알림

### 9.1. 기본 정책

- 발송은 `NotifyRouter`에 맡긴다. 라우트는 (category `hotdeal`, purpose `recommend`)이고,
  없으면 `AutoTopicProvisioner`가 기본 chat 에 토픽을 만든다.
- 설정은 `crawl_config('hotdeal_notify')`로 관리한다 (시스템 관리 화면에서 수정).
  `enabled`(기본 false), `score_threshold`(5.0), `daily_limit`(5), `quiet_start`~`quiet_end`(23:00~08:00),
  `timezone`(Asia/Seoul), `max_age_hours`(6), `web_url`(메시지의 피드 링크, 비우면 생략).
- 배포 직후 알림이 몰리지 않도록 기본은 꺼 둔다. 관찰 모드 결과를 보고 켠다.
- 대상: 피드백 없음, 판정(8.4) 통과, 콜드스타트 인기 항목 아님, 아직 안 보냄, 게시 `max_age_hours` 이내,
  점수 `score_threshold` 이상. 점수 높은 순으로 오늘 남은 상한만큼 보낸다.
- 일일 상한은 설정된 시간대의 0시부터 센다. 조용한 시간에는 보내지 않는다 (자정을 넘기는 구간 허용).
- 수집 주기마다 수집 → 재평가 → 판정 → 알림 순서로 실행한다.

### 9.2. 메시지 구성

- 제목
- 가격·배송비 등 핵심 정보
- 소스
- 짧은 추천 이유
- 원문 링크
- 웹 피드 항목 링크

v1에서는 Telegram 피드백 버튼 없이 시작한다.
추가할 경우 네이티브 리액션 수집 대신 인라인 버튼을 쓰고,
웹과 같은 피드백 처리 로직에 연결한다.

### 9.3. 발송 신뢰성

- 발송 성공이 확인된 항목만 `hotdeal_feed_item.notified_at`을 남긴다. 하루 상한과 재발송 방지에 쓴다.
- 실패한 항목은 기록하지 않아 다음 주기에 다시 후보가 된다.
- 같은 항목의 성공 재발송은 `notify_log`의 (route, payload key `hotdeal:{feed_item_id}`) 확인으로 막힌다.
  발송은 성공했는데 `notified_at` 기록이 실패해도 중복 발송되지 않는다.

Telegram 발송과 DB 저장을 하나의 원자적 트랜잭션으로 묶을 수 없으므로,
외부 발송의 정확히 한 번 실행을 보장한다고 표현하지 않는다.

## 10. 중복 및 신선도 정책

### 원본 중복

- 소스·공급자·원본 키로 중복 제거
- 재수집 시 최신 메타데이터 갱신

### 소스 간 동일 딜

- 정규화한 동일 구매 링크부터 중복 판정
- 제목·가격 기반 판정은 보수적으로 적용
- 상품 옵션이나 판매처가 다른 항목을 잘못 합치지 않도록 주의
- 동일 딜의 짧은 기간 내 중복 알림 억제

### 최초 실행

- 기존 항목을 기준선으로 수집한다.
- 과거 항목을 일괄 알림하지 않는다.
- 초기 웹 피드 노출 범위와 소스별 최대 게시물 연령은 별도로 설정한다.

### 보존

scoophub `DataRetentionJob`(90일)에 핫딜 테이블을 포함할지는 M6에서 결정한다.
이미 피드백한 항목은 보존 대상에서 제외하는 방향으로 검토한다.

## 15. 초기 성공 기준

첫 검증 목표는 소스 개수가 아니라 추천의 유용성이다.

> 뽐뿌 하나만 연결해도 사용자가 며칠 동안 웹 피드를 계속 확인하고,
> 추천이 자신의 관심에 맞는다고 느끼는가?

확인할 지표:

- 일일 추천 항목 수
- 좋아요·싫어요 비율과 이유
- 중복 딜 및 종료된 딜 노출 빈도
- Telegram 알림의 유용성과 피로도
- 관심도 변경 후 추천 결과의 변화

피드백 비율만으로 만족도를 단정하지 않는다.
무반응은 부정 평가로 처리하지 않으며, 실제 사용 의견을 함께 확인한다.

추천 만족도가 낮다면 소스 확장보다 매칭·중복·신선도·알림 정책을 먼저 개선한다.
