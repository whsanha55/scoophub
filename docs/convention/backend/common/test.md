# Test Convention (Backend 공통)

언어와 무관한 백엔드 테스트 규칙이다. 도구와 작성법은 언어별 `test.md`를 따른다.

## 1. E2E 테스트

E2E는 테스트 코드가 아니라 셸 스크립트로 쓴다. 실제 서버를 띄우고 `curl`로 API를 호출한다.

- API를 추가하거나 기존 API의 동작을 바꾸면 해당 E2E 스크립트를 함께 고친다. 스크립트가 없는 리소스면 새로 만든다.
- 백엔드 코드를 바꾸면 작업을 마치기 전에 관련 E2E를 실행한다 (`scripts/e2e/run-all.sh {resource}`). 인증, 설정, 공통 코드를 바꿨으면 전체를 실행한다.
- E2E가 실패하면 원인을 가른다. 의도한 동작 변경이면 스크립트를 고치고, 아니면 코드를 고친다. 모두 통과할 때까지 반복한다.
- 빌드한 실행 파일(bootJar, Go 바이너리)을 운영과 같은 방식으로 띄운다. 내부 의존성을 mock으로 바꾸지 않는다.
- DB 같은 인프라는 Docker Compose로 띄운다. 제3자 외부 API만 스텁 서버(WireMock 등)로 대체하고, 외부 API 주소는 설정으로 바꿀 수 있게 둔다.
- 로그인은 인증 흐름을 스텁으로 끝까지 타서 실제 토큰을 받는다. 토큰을 직접 만들지 않는다.
- 성공 흐름과 대표 실패(인증 실패, 검증 오류)를 검증한다. 세부 분기는 단위 테스트에서 검증한다.
- 스케줄러만 만드는 데이터처럼 API로 만들 수 없는 데이터만 SQL로 직접 넣는다.
- 스크립트끼리 데이터를 공유하지 않는다. 각 스크립트가 필요한 데이터를 고유한 키로 직접 만든다.

구성:

```text
scripts/e2e/
├── server.sh            # start | stop | status — 컨테이너 기동, 앱 실행, health 대기
├── run-all.sh           # 전체(또는 일부) 실행, 결과 요약, 실패 시 exit 1
├── lib.sh               # 공통 함수 (요청, 응답 검증, 로그인, 스텁 등록)
├── docker-compose.yml   # DB, 스텁 서버
├── application-e2e.yml  # E2E 설정 (외부 API 주소를 스텁으로)
├── stub/                # 기본 스텁 매핑
└── {resource}-e2e.sh    # 리소스 단위 스크립트
```

- 스크립트는 `curl`, `jq`만 쓰고 Bash 3.2(macOS 기본)와 호환되게 쓴다.
- 요청마다 메서드, 경로, HTTP 상태, 응답 본문을 출력한다. 실패하면 무엇을 기대했는지 출력하고 바로 종료한다.
- 실행 방법은 README에 적는다.
